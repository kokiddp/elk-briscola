# 3. SignalR over raw WebSockets

Date: 2026-05-19

## Status

Accepted

## Context

The real-time channel for elk-briscola needs to carry:

- Per-game state snapshots (server → connected players + spectators in a game group).
- Lobby pushes (open-game create / update / start / end, lobby chat).
- Per-user invalid-move rejections (server → caller only).
- Reconnect-safe semantics (drop a connection, reattach the same identity, resume).

Two channel choices were considered:

1. **Raw WebSockets** with a hand-rolled framing protocol on top.
2. **ASP.NET Core SignalR** with `@microsoft/signalr` on the client.

We are a .NET 10 / Angular 21 stack; both sides have first-party SignalR support.

## Decision

We use SignalR.

- **Two hubs.** `LobbyHub` (`/hubs/lobby`) and `GameHub` (`/hubs/game`). A single WebSocket per hub per authenticated user; both stay up while the user is logged in (the Angular client owns lifecycle in [LobbyService](../../frontend/src/app/features/lobby/lobby.service.ts) / [GameService](../../frontend/src/app/features/game/game.service.ts)).
- **Groups for fan-out.** `lobby:open` for the open-game list; `game:{id}` for an active game's players; `game:{id}:spectators` for read-only watchers. The hub layer routes pushes via `IHubContext` group invocations.
- **Authentication.** JWTs are passed via `@microsoft/signalr`'s `accessTokenFactory` option, which ASP.NET Core's SignalR JWT integration consumes from the `?access_token=` query string on the negotiate + WebSocket handshake. The `Context.UserIdentifier` is then `sub` from the JWT.
- **Per-recipient pushes.** When a snapshot must differ per user (different hand contents), the dispatcher fans out N calls — one per `User` via `Clients.User(...)` — rather than one group call. This is what enables per-recipient redaction (see [ADR 0002](0002-server-authoritative-game-state.md)).
- **Transport fallbacks.** Allow Long Polling + Server-Sent Events as transport fallbacks in `AddSignalR`. WebSocket is the happy path; the fallback lets corporate proxies that block WebSockets still work for read-mostly traffic.

## Consequences

**Positive.**

- We don't write a framing protocol. SignalR handles connection IDs, reconnection metadata, transport upgrades, group membership, and per-method message envelopes.
- The DTO surface is typed end-to-end: server-side records → client-side TS interfaces, with the wire format auto-derived (JSON, camelCase by default).
- The `@microsoft/signalr` client implements auto-reconnect with backoff. `LobbyService.onreconnected` re-subscribes to `lobby:open` after a reconnect.
- Groups make spectator-only pushes trivial — they're in `game:{id}:spectators`, not `game:{id}`, so we never accidentally leak hand information into the spectator stream.

**Negative / costs.**

- SignalR is .NET-specific. A non-.NET service that wants to push into this bus has to either run the SignalR Core protocol or talk to the API via REST. Acceptable: we have no such service in v1.
- Documentation is dual-channel: REST is auto-generated by Swashbuckle; SignalR is hand-maintained in `backend/src/Briscola.Api/docs/asyncapi.json`. The hand-maintained file is a liability — adding a field on the wire requires a docs update. Mitigation: the AsyncAPI viewer is mounted at `/docs/asyncapi` and the JSON is in source control, so review catches drift.
- Multi-instance scale-out needs a Redis backplane. We pay that cost in v2 if and when we shard rooms.

**Trade-offs explicitly accepted.**

- The wire format is JSON, not MessagePack. JSON is observable in browser devtools and grep-friendly in tcpdumps; the bandwidth savings of MessagePack don't matter for a 40-card-per-game protocol.
- We use named hub methods over a single generic push channel because typed methods make Swagger / AsyncAPI useful and let SignalR client code generate strongly-typed callbacks.
